Formel-Struktur
Zwei Outcomes gemeinsam fitten, optional mit geschätzter Residualkorrelation zwischen ihnen.
Für einen Response eine echte nichtlineare Funktion (z.B. eine Zerfallskurve) statt einer Summe linearer Terme — jeder nichtlineare Parameter bekommt seine eigene kleine Formel.
Prädiktor-Typen
Ein Prädiktor darf eine flexible, glatte (nicht notwendig lineare) Kurve haben — s(x).
Ordinaler Prädiktor (z.B. Bildungsstufe): Effekt monoton, aber Schrittgrößen nicht als gleich angenommen — mo(x).
Ein Prädiktor darf eine flexible, glatte Kurve haben — wie s(x), aber über einen Gaussian Process statt einer Spline-Basis modelliert — gp(x).
Der beobachtete x-Wert ist eine verrauschte Messung eines latenten wahren Werts — me(x, sd_x).
Daten-Eigenheiten
Zwei Wege: brms-interne Imputation (mi()) oder externe Multiple Imputation mit mice + brm_multiple().
Response-Werte sind nur bis zu einer Grenze bekannt (cens(), z.B. "länger als 30 Tage überlebt") oder können bestimmte Werte prinzipiell nicht annehmen (trunc(), z.B. Messgerät-Range).
Gruppierung & Korrelation
Statt "alles korreliert automatisch": explizit unkorreliert (||) oder nur bestimmte Terme über ein gemeinsames ID-Tag (|p|, |q|, …).
Eine Beobachtung gehört zu MEHREREN Leveln derselben Gruppierung gleichzeitig, z.B. mit Gewichten (Schüler:in mit zwei Lehrkräften dieses Halbjahr) — mm().
Beobachtungen sind über Zeit (ar/ma/arma) oder Raum (car) korreliert, nicht unabhängig — z.B. Messwiederholungen mit Trend-Resten, oder Regionen mit Nachbarschaftsstruktur.
Verteilung & Priors
Viele Kandidaten-Prädiktoren, vermutlich nur wenige davon wirklich relevant: der Horseshoe-Prior schrumpft die meisten Koeffizienten automatisch Richtung Null. Danach mit projpred die wichtigsten Prädiktoren identifizieren.
Deine Beobachtungen stammen vermutlich aus mehreren unbeobachteten Untergruppen mit jeweils eigener Verteilung (z.B. zwei Reaktionszeit-Regimes, "schnell geraten" vs. "überlegt") — mixture(fam(), fam(), ...) statt einer einzigen Familie.
Ein in R berechneter Wert (z.B. ein datenabhängiger Mittelwert/SD für einen Prior) ist Stan sonst unbekannt — stanvar() deklariert ihn als echte Stan-Variable und übergibt den Wert.

⚠ Wie dieses Tool zu benutzen ist

Das ist kein vollautomatischer Modell-Builder. Für Standardmodelle nimm den brms Model Builder — dort ist der generierte Code direkt lauffähig.

Dieses Tool ist für seltene, fortgeschrittene Bausteine gedacht, die im Standard-Model-Builder keinen Platz finden — multivariate Modelle, Random-Effects-Korrelationsstrukturen, Splines/Gaussian Process, nichtlineare Formeln, Autokorrelation, Multi-Membership, Zensierung/Trunkierung, Hurdle- und ordinale Familien, Messfehler und fehlende Werte, unter anderem. Es setzt Erfahrung mit brms voraus.

Die Sidebar links baut den Code oben rechts live auf. Jede Dokumentationskarte weiter unten hat einen Button "✓ Direkt anwenden", der die jeweilige Einstellung direkt in das Modell übernimmt. Zusätzlich hat jede Karte ein einklappbares Feld "🧪 Datensimulation" mit R-Code, der einen kleinen Testdatensatz für genau diesen Baustein erzeugt. Der Code im Feld lässt sich frei bearbeiten; sobald das geschieht, überschreiben Änderungen in der Sidebar ihn nicht mehr automatisch — "🔄 Neu generieren" baut ihn bewusst aus dem aktuellen Sidebar-Zustand neu auf, "↺ Zurücksetzen" verwirft auch den Sidebar-Zustand und beginnt wieder bei einem leeren Modell.

Priors werden bewusst nicht geraten — der generierte Code enthält deshalb keinen automatisch erzeugten priors <- c(...)-Block, sondern ruft get_prior() auf, das anzeigt, welche Klassen/Koeffizienten brms für das jeweilige Modell erwartet.

Der "✓ Formaler Check" prüft nur auf strukturelle Auffälligkeiten (Klammern, fehlende Argumente, Tag-Konsistenz) — er ersetzt keinen echten Testlauf in R (z.B. make_stancode() oder ein paar Iterationen mit sample_prior="only").
